# Репетитор CRM — API

Бэкенд Telegram Mini App: ученики, занятия, деньги и автонапоминания.
NestJS + PostgreSQL + Prisma. Бот на grammY живёт в этом же процессе.

## Запуск локально

Нужен работающий Postgres. На macOS:

```bash
brew install postgresql@17
brew services start postgresql@17
createuser -s tutor          # если роли ещё нет
createdb -O tutor tutor_crm
```

Дальше:

```bash
cp .env.example .env         # заполнить BOT_TOKEN и JWT_SECRET
npm install
npm run prisma:migrate       # применить миграции
npm run start:dev            # http://localhost:3000/api
```

Проверка: `curl http://localhost:3000/api/health` → `{"status":"ok","db":"ok"}`.
Эндпоинт ходит в базу, поэтому отвечает 200 только при живом соединении.

## Переменные окружения

Все обязательные проверяются на старте — приложение без `BOT_TOKEN`
падает сразу с понятным текстом, а не через час на первом запросе.

| Переменная | Зачем |
|---|---|
| `DATABASE_URL` | строка подключения к Postgres |
| `BOT_TOKEN` | токен из @BotFather; им же проверяется подпись `initData` |
| `BOT_USERNAME` | имя бота без `@`, для ссылок-приглашений |
| `JWT_SECRET` | подпись сессионных токенов (`openssl rand -base64 32`) |
| `CORS_ORIGINS` | origin мини-аппа, через запятую |
| `PORT` | порт, по умолчанию 3000 |
| `BOT_MODE` | `polling` (локально) или `webhook` (прод) |
| `BOT_PUBLIC_URL` | только для webhook: публичный адрес API |
| `BOT_WEBHOOK_SECRET` | только для webhook, ≥16 символов |
| `ADMIN_TG_ID` | Telegram ID администратора: команда `/stats` и фидбэк репетиторов — только ему |
| `MINI_APP_URL` | адрес мини-аппа (https): кнопка «Открыть кабинет» в ответе бота на `/start` |
| `AI_MATERIALS_LIMIT` | сколько материалов ИИ соберёт одному репетитору; не задан — 10, `0` — без лимита; администратору не считается |

`.env` в гите нет и быть не должно — только `.env.example`.

## Схема данных

Семь таблиц, см. `prisma/schema.prisma` — там каждое решение прокомментировано.
Коротко о том, что важно понимать при работе с API:

**Деньги — целые копейки.** 1500 рублей это `150000`. Ни одного `Float`:
дробные рубли рано или поздно дают 1499.9999999 и ломают отчёты.

**Цена копируется в занятие.** `Lesson.price` — снимок `Student.price`
на момент создания. Поднятие цены ученику не переписывает прошлые
месяцы задним числом.

**`paidAt` вместо `paid: boolean`.** Та же стоимость хранения, но появляется
ответ на вопрос «сколько денег пришло за март».

**`startsAt` — абсолютный момент (timestamptz)**, плюс `User.timezone`.
Строка «16:00» ничего не значит для планировщика, пока неизвестна зона.

**Ученик без `userId` — нормальное состояние.** Репетитор завёл карточку
вручную: имя и цена есть, канала связи нет. Писать в Telegram можно только
после того, как ученик сам нажал `/start` и `userId` проставился.

**Удаление ученика — мягкое** (`archivedAt`). Иначе вместе с карточкой
пропадает вся финансовая история за год.

**Таблица `reminders` существует ради `@@unique([lessonId, kind])`.**
Планировщик перезапускается, тикает дважды, падает после отправки но до
записи результата. Без уникального ключа ученик получает одно и то же
напоминание три раза подряд.

## Авторизация

Мини-апп входит по `initData` — строке, которую Telegram подписывает
токеном бота.

```
POST /api/auth/login   { "initData": "<window.Telegram.WebApp.initData>" }
  → { accessToken, user: {...}, tutorId }

GET  /api/auth/me      Authorization: Bearer <accessToken>
  → { userId, tutorId }
```

Дальше каждый запрос идёт с заголовком `Authorization: Bearer <token>`.

### Что здесь защищает данные

**Подпись `initData` проверяется по HMAC-SHA256** ([init-data.ts](src/telegram/init-data.ts)).
Без этой проверки клиент присылает какой угодно `tgId` и получает чужой
кабинет. Сравнение хешей — `timingSafeEqual`: обычное `===` выдаёт подпись
побайтово по времени ответа.

**Срок жизни подписи — 24 часа.** Подпись валидна вечно, поэтому
перехваченная строка работала бы бесконечно; ограничивает только `auth_date`.

**Закрыто по умолчанию.** `JwtAuthGuard` висит глобально, роут открывается
только явным `@Public()`. Забыть повесить защиту на новый эндпоинт нельзя —
можно только осознанно снять.

**Причины отказа клиенту не сообщаются.** «Просрочен», «подпись не сошлась»
и «нет user» снаружи выглядят одинаково: подробности помогают подбирать
подпись. В логах причина есть.

**В JWT только `sub` (User.id) и `tid` (Tutor.id).** Ни `tgId`, ни username:
токен лежит на клиенте, и лишних данных в нём быть не должно.

**`tgId` не отдаётся в ответах API.** Клиент и так знает свой Telegram ID,
а для запросов он не нужен — идентификация идёт по внутренним UUID.

**Лишние поля в теле запроса отклоняются** (`whitelist` +
`forbidNonWhitelisted`), чтобы клиент не мог дописать в запрос ключ,
о котором DTO не знает.

**Частота ограничена** 60 запросами в минуту: `/auth/login` — единственная
открытая точка, и подбор подписи должен стоить дорого.

## Эндпоинты

Все, кроме `/auth/login` и `/health`, требуют `Authorization: Bearer <token>`.

### Профиль репетитора

```
GET    /api/tutor   профиль кабинета; onboardedAt: null — показать онбординг
PATCH  /api/tutor   { displayName?, subjects?, defaultPrice?, notifyBeforeHours?,
                      notifyBeforeMinutes?, notifyDebtReminder?, onboarded? }
```

Напоминания из профиля копируются в настройки каждого нового ученика,
имя и предметы подписывают текст приглашения.

### Ученики

```
GET    /api/students              ?includeArchived=true&skip&take
GET    /api/students/:id
POST   /api/students              { name, price, note?, notify? }
PATCH  /api/students/:id          { name?, price?, note? }
PATCH  /api/students/:id/notify   { enabled?, beforeHours?, ... }
POST   /api/students/:id/archive  скрыть, сохранив историю
POST   /api/students/:id/restore
DELETE /api/students/:id          только если занятий нет (иначе 409)
```

### Занятия

```
GET    /api/lessons          ?studentId&status&from&to&skip&take
GET    /api/lessons/summary  ?from&to — по умолчанию текущий месяц
GET    /api/lessons/:id
POST   /api/lessons          { studentId, startsAt, duration?, price?, note? }
POST   /api/lessons/bulk     { lessons: [{ studentId, startsAt, duration?, price?, note? }] } — до 300; занятия, уже стоящие у ученика на это время, пропускаются
POST   /api/lessons/series   { series: [{ studentId, startsAt, duration? }] } — занятия «каждую неделю»; создаются на 12 недель вперёд и продлеваются раз в час
DELETE /api/lessons/series/:id  ?from — оборвать серию: запланированные занятия с этого момента удаляются
POST   /api/lessons/import/recognize  { image?, text? } — расписание с фото (data URL) или из текста → { rows }; в базу не пишет
PATCH  /api/lessons/:id      { startsAt?, duration?, price?, status?, paid?, note? }
DELETE /api/lessons/:id
```

`summary` возвращает `{ from, to, doneCount, plannedCount, earned, owed }`.
`earned` — проведённые и оплаченные, `owed` — проведённые без оплаты,
отменённые не входят ни в одну сумму. Всё в копейках.

### Правила, заложенные в API

**Цены — копейки.** 1500 руб. = `150000`. Дробное значение отклоняется.

**`startsAt` — ISO 8601 со смещением**: `2026-10-01T16:00:00+03:00`.
Строка без зоны неоднозначна, планировщик не поймёт, когда занятие
наступает на самом деле.

**Цена занятия фиксируется при создании.** Не передал `price` — возьмётся
из карточки ученика и останется навсегда. Поднятие цены не переписывает
прошлые месяцы.

**Оплата отмечается флагом `paid`, не датой.** Момент оплаты ставит сервер:
иначе платёж можно задатировать и исказить отчёт за период. Повторное
`paid: true` не сдвигает уже записанную дату.

**Ученик архивируется, а не удаляется**, пока у него есть занятия —
`DELETE` ответит 409. Иначе вместе с карточкой пропала бы вся
финансовая история.

**Архивному ученику нельзя назначить занятие** — сначала восстановить.

### Приглашения

```
POST   /api/students/:id/invite   создать ссылку
DELETE /api/students/:id/invite   отозвать
```

`POST` возвращает `{ code, link, expiresAt, message }`, где `message` —
готовый текст для отправки ученику.

**Бот не может написать первым** — Telegram это запрещает. Поэтому порядок
такой: репетитор создаёт ссылку, отправляет её ученику любым способом,
ученик открывает и нажимает «Начать». Бот получает `/start <code>`,
привязывает аккаунт и с этого момента может присылать напоминания.

Статус карточки: `NONE` → `INVITED` (ссылка создана) → `ACCEPTED`
(ученик подключился).

### Как защищены приглашения

Код приглашения — это **secret**: он даёт право привязаться к карточке
ученика. Отсюда всё остальное.

**16 символов, ~79 бит энтропии** ([invite-code.ts](src/invites/invite-code.ts)).
При 10 символах подбор ещё мыслим, при 16 — нет. Алфавит без похожих
глифов (`0/O`, `1/l/I`): коды иногда переписывают руками.

**`randomInt` из `node:crypto`, не `Math.random`.** Последний предсказуем
по нескольким выданным значениям — зная один код, можно было бы вычислить
следующие. `randomInt` заодно исключает modulo bias, из-за которого при
`byte % 31` первые символы алфавита выпадали бы чаще (проверено тестом
на равномерность).

**Одноразовый.** Повторный `/start` с тем же кодом не привяжет второго
человека к той же карточке.

**Срок жизни 72 часа**, после чего ссылка мертва.

**Перевыпуск гасит прошлые коды.** Иначе у одного ученика накапливался бы
набор действующих ссылок, каждая из которых — secret.

**Отзыв работает мгновенно** — `DELETE` убивает выданную ссылку.

**Защита от гонки.** Два одновременных `/start` с одним кодом: гашение
идёт через `updateMany ... where usedAt: null`, второй получает `count: 0`
и откатывает транзакцию. Проверено тремя параллельными вызовами —
привязался ровно один.

**Форма кода проверяется до базы.** В `/start` прилетает что угодно от
любого человека в Telegram, включая инъекции и гигантские строки.

**Бот отвечает одинаково на все причины отказа** — иначе по тексту можно
отличить «кода нет» от «код занят» и подбирать ссылки.

### Изоляция кабинетов

`tutorId` берётся **только из JWT**, никогда из параметров запроса —
попросить данные другого кабинета клиент физически не может.

Каждый метод сервиса принимает `tutorId` первым аргументом и подставляет
его в `where`. Без этого запрос просто не собирается, поэтому забыть
скоуп нельзя.

Чужой объект и несуществующий дают **одинаковый 404**: разные ответы
позволили бы перебором выяснить, какие id существуют.

Наружу идёт явный `select`, а не вся строка — новое внутреннее поле
в схеме не утечёт в API само по себе. В частности, не отдаётся `userId`
(внутренняя связь с аккаунтом Telegram).

Поля `source`, `inviteStatus` и `userId` клиент менять не может: их
проставляет только сервер по факту подключения ученика к боту.

## Бот

Живёт в том же процессе, что API. Умеет одно: по `/start <code>`
привязать аккаунт Telegram к карточке ученика.

**Локально — polling**, публичный URL не нужен. `BOT_MODE=polling`.

**На проде — webhook**: `BOT_MODE=webhook`, плюс `BOT_PUBLIC_URL`
и `BOT_WEBHOOK_SECRET` (`openssl rand -hex 32`). Приложение проверяет
их на старте и не запустится без секрета: webhook-эндпоинт открыт
для Telegram, и без проверки заголовка
`X-Telegram-Bot-Api-Secret-Token` любой желающий смог бы присылать
поддельные «обновления» с чужим `/start`. Сравнение секрета —
`timingSafeEqual`.

Два решения про устойчивость:

**Сбой подключения к Telegram не валит API.** Ученики и деньги доступны
и без бота, поэтому неудачный `setWebhook` пишется в лог, а приложение
поднимается. Иначе перезапуск на хостинге в неудачный момент оставил бы
всё лежащим.

**Webhook всегда отвечает 200**, даже когда обработчик упал. Telegram
повторяет обновление, пока не получит 2xx — отдать 500 значит зациклить
доставку одного сообщения.

Запустить бота в webhook-режиме локально нельзя без туннеля
(ngrok и подобные): Telegram должен дотянуться до `BOT_PUBLIC_URL`.

## Статистика пилота

Нужна, чтобы понять, нравятся ли репетиторам материалы: журнал событий в таблице
`events`, фидбэк в `feedback`, вопросы бота в `surveys`.

Сервер пишет события сам, на действиях с материалом (`MaterialsService`): сборка,
пересборка, правка, удаление, скачивание, отправка, итог проверки, упор в лимит.
Приложение присылает только то, чего сервер не видит: `POST /api/events` с
`material_rating` (оценка 👍/👎 и причина) и `upgrade_interest` («хочу больше материалов»).
`POST /api/feedback { text, screen? }` — «Написать разработчику»; текст сохраняется
и сразу уходит администратору в Telegram.

**Приватность.** В `props` — только числа, коды и короткие метки (`src/events/event-names.ts`):
строка длиннее 40 символов отбрасывается целиком, у клиентских событий поля разбираются по
формату, а предмет пишется только из известного списка. Тем, текстов материалов и имён
учеников в журнале нет.

**Смотреть цифры** — в боте, у администратора (`ADMIN_TG_ID`):
`/stats` — сводка пилота; `/stats @username` — последние 40 событий одного репетитора.
Остальным бот на `/stats` отвечает как на любое сообщение.

**Вопросы бота** (`SurveysService`, раз в час): на следующий день после отправки материала
без ответов — «Отправили ученику?», через неделю после регистрации — «Расстроитесь, если
генератор пропадёт?». Каждый вопрос задаётся один раз (`@@unique` на `surveys`).
При `BOT_MODE=off` не задаются.

## Напоминания

Планировщик живёт в том же процессе: cron раз в минуту забирает
напоминания, которым пришло время, и отправляет их через бота.

Напоминания создаются автоматически при создании занятия и
пересоздаются при сдвиге времени или смене статуса. Ученику без
подключённого аккаунта ничего не планируется — писать некуда.

По каждому занятию планируются два: за `beforeHours` часов и за
`beforeMinutes` минут (0 — выключено). Отдельно, раз в сутки в 11:00,
уходит напоминание о неоплаченных занятиях — одним сообщением
с общей суммой, а не по письму на каждое занятие.

Время в сообщениях — **в таймзоне репетитора** (`User.timezone`):
он ставит занятия в своём времени, и «16:00» в напоминании должно
совпадать с тем, что он видит в приложении.

### Почему это не ломается

**Дубли невозможны.** Запись в `reminders` с `@@unique([lessonId, kind])`
плюс `sentAt`: отправленное напоминание закрыто и повторно не берётся.
Планировщик может перезапуститься, тикнуть дважды или упасть после
отправки — ученик получит сообщение один раз.

**Тики не накладываются.** Медленный Telegram иначе дал бы два
параллельных прохода по одной выборке; пока предыдущий идёт,
новый тик пропускается.

**Один сбой не останавливает рассылку.** Каждое напоминание
обрабатывается в своём `try`; ученик, заблокировавший бота, не мешает
остальным получить свои.

**Три попытки, потом сдаёмся** (`attempts`). Моргнула сеть — повторим
на следующем тике. Заблокировал бота (403) — закрываем сразу,
повторять бессмысленно.

**Просроченное не отправляется.** Если сервис лежал, напоминание
«занятие через час» про занятие, которое прошло два часа назад,
только смутит ученика — такие пропускаются с отметкой в логе.

**Условия перепроверяются перед отправкой.** Занятие отменили, ученика
заархивировали, уведомления выключили после планирования — напоминание
закрывается, не отправляясь.

**Долги не дублируются** даже при двойном запуске cron: отметка
`kind: DEBT` ставится до отправки, и `@@unique` не даст создать вторую.
Не ушло — отметка снимается для следующей попытки.

**Окно тишины не реализовано.** Поля `quietFrom`/`quietTo` в схеме и API
остались, но планировщик их не читает. Долги уходят в 11:00 —
сообщение об оплате в 3 утра приводит к блокировке бота.
